## 理由

1. **API 长等待不能全部解释为思考过多。** 行李箱第 12 轮 elapsed=349.777 秒，响应 usage 仅 completion_tokens=273、reasoning_tokens=20、prompt_tokens=46457、cached_tokens=41600。另有第 28 轮 160.472 秒/7134 reasoning tokens，确有长生成。前者明显还需要服务端排队、首 token 延迟、吞吐及重试明细才能继续归因；控制台没有找到明确的提供方重试事件，不能臆断为限流或重试。
2. **没有实际反复读技能的证据。** 按原始 assistant.tool_calls 计数，7 条各自所用的 6 项技能均只 read_file 一次。补017 的 flight-control/target-detection 在后半程首次读取，不能按它们出现得晚就算重读。每轮请求携带已有工具结果，因此累计快照会反复出现同一段技能与历史结果，但不等于再次调用工具。
3. **缓存本批正常出现。** 行李箱共报告 cached_tokens=1236480、prompt_tokens=1748674；补017 分别为 1090944/1328871。上表按已报告缓存值求和，缺字段不能证明命中为零。累计输入 token 包含每轮重传的历史，不能视作独立新增 token 或直接换算账单。usage 没有逐角色 token；按累计消息字符统计，行李箱 tool 内容约 195 万字符、assistant 约 172 万，补017 分别约 149 万/143 万，不能将字符占比当 token 占比。
4. **行李箱首次不可行返回太笼统。** 轨迹 messages[26] 只返回 `solver terminated: infeasible`，随后再次求解仍无新诊断，messages[37:64] 多次检索/读取 allocation、scheduler、worker 和求解器。末端推导得到的真实原因是 073 必须等待 258，满足共担重叠与返航至少需要 2390.144729 秒，超过 2386.8 秒预算 3.344729 秒。应由工具返回可证明的数值，而不是让模型逆向求解代码。五机备选仍改变了原要求，必须待接受。
5. **补017 有两段可避免的探索。** 组装前为判断同机先后与独立并行、以及 constraints 属于哪个入口，多次读取包装层和 runtime；组装失败 messages[49] 只含 394 的首个错误，未保留 270/292 的通过状态，模型在 messages[53:60] 阅读并复制组装循环，先写 /tmp 失败再写工作区执行。后续又借旧请求查意图文件格式。这些是接口/诊断缺口和模型未遵守已有停止规则的共同问题，不能仅增加“更简洁”提示解决。

## 修改

1. `uav_runtime/atomic/allocation.py`：仅在所有候选必须出动、某作业恰有两架合格机且各自只有此作业可做时，计算重叠要求下的等待与返航时间必要下界。只在原求解器已判不可行后补诊断；未证明具体原因时返回 `UNDETERMINED`。不新增求解、不改变约束、预算或解的选择。
2. `skills/flight-control/scripts/assemble_plan.py`：坐标/动作验证失败后继续检查其他参与机，最终一次返回逐机检查状态。整体仍抛 AtomicError、退出码 2、artifact_created=false；保留首错 message/uav_id/max_distance_m，不发布部分动作产物或暗示已可下发。成功时 compact/full/off 输出不变。
3. skills：原有失败规则改为消费上述诊断，未知原因如实保留；结尾不能遗漏尚未修复的动作失败。trajectory 明确数量/允许集合属于 allocate.constraints；combined-tasks 澄清同机顺序链与独立并行的能力检查范围。没有增加固定距离、工具次数上限或通用再次确认。
