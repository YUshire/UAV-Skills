# 任务入口与编排

## 一、请求分类

| 类型 | 示例 | 处理 |
|---|---|---|
| 单项查询 | 查 UAV-001 的电量；教学楼在哪 | 读 data-query |
| 单项计算 | 教学楼东北 20 米的坐标；某区域的搜索框 | 读 spatial-compute |
| 单项航迹 | A 到 B 的航线和距离 | 读 trajectory-generation |
| 动作序列校验 | 检查这段动作序列是否合法 | 读 flight-control，只做 dry-run |
| 感知单项 | 给 UAV-002 开启行人识别；还剩哪些目标没找到 | 读 target-detection |
| 分配咨询 | 我有五架机，搜索教学楼和图书馆怎么分配 | 读 mission-orchestration，只返回分配方案 |
| 飞行任务 | 去教学楼看看；搜索穿红衣服的人；巡逻广场两圈 | 查询补齐、规划校验后下发 |
| 只规划 | ……只规划不执行 / 先给方案 | 补齐本次方案需要的计算和dry-run|
| 确认卡的回复 | 对上一张待确认方案说确认、修改、取消或追问 | 第三节“用户对确认卡的回复” |
| 运行中指令 | 暂停、继续、全部返航、取消任务、停止跟踪 | 第四节 |
| 中央事件通知 | 待决策、异常、发现目标、任务结束 | 第四节 |
| 状态或原因询问 | 现在进度如何？为什么停了？ | 第四节只读查询 |

## 二、飞行指令校验

**先理解、查库补齐，再继续规划。** 用户无需按接口字段描述任务。按整句话及上下文确定动作、地点、对象和顺序；已给信息直接沿用，能查到的地点、区域、机况和资源直接采用，未指定的常规参数使用本节默认值。只有查询后仍缺必要事实，或不同解释会实质改变任务且上下文无法判断时，才询问最少缺项。

**日常表达**：

| 表达 | 理解与处理 |
|---|---|
| 单独的“去A”“先去A，再去B” | 到达或途经A，保留先后顺序；“去A看看/巡逻”整体归入该地点的探索/巡逻任务 |
| “去看看”“查看某区域”“搜索某地”“搜一下某地”“扫一遍” | 上下文有目标则沿用目标；没有目标则按无目标区域查看/探索，不追问“要找什么” |
| “找红衣服的人”“搜那辆车” | 带目标搜索；从原话和上下文提取已有对象及特征 |
| “沿边走一圈”“绕着巡两圈” | 边界巡逻，保留圈数；范围优先用用户描述，否则用地点库登记区域 |
| “某地周围N米扫一遍”“某地周围N米的圈巡两圈” | 按地点区域中心（仅有点位时用该点）、半径N米整理，保留动作和圈数；明确说距建筑边界外扩时保留外扩含义 |
| “先……再……接着……最后……” | 明确的执行顺序，保留到任务表示和能力核对中 |

这些是意图解析规则；具体航迹、范围和完成条件仍由相应工具核对。明确要求固定往返航线或整区覆盖时保留该要求。

| 条件 | 判断标准 | 仍需解决的情况 |
|---|---|---|
| 任务意图 | 按上述日常表达区分带目标搜索、无目标探索/建图、巡逻和单纯飞行 | 仅说“处理一下”且无上下文，无法确定动作 |
| 任务地点 | 地名、经纬度或相对位置；只有方向+距离时，按下述“相对基准”区分指定单机与地点库默认位置 | “去附近搜索” |
| 区域 | 只支持圆形和矩形；用户给的形状、尺寸优先，否则直接使用地点库登记的完整区域 | 查库后仍只有点位且无范围；用户指定圆形但上下文和记录均无适用半径 |
| 相对方位 | 东西南北等绝对方位可计算；左、右、前、后从上下文或可用状态取得朝向 | 仍无朝向时才询问，不能将“左前方”固定解释为西北 |
| 参数合理 | 航高在 (0.3, 3.0] m；速度、半径、长宽 > 0；圈数为正整数；经纬度合法 | “速度 -5 m/s”；“航高 10 米” |
| 指令无冲突 | 各项要求不互相矛盾 | “用最大高度 1 米的机，航高 2 米” |
| 完成条件与能力 | 区分任务意图、完成条件、结束动作；工具成功还须能表达用户明确的条件 | 数量去重、全任务总时限、自定义跟踪时长等不能靠格式校验变成已支持 |

- 数值超出工具或机型范围时，指出具体冲突并只询问冲突参数。工具中搜索和探索均用几何标签 `task_type="search"`，是否配置目标取决于用户语义。
- “可疑目标”先结合当前任务和历史描述解析；仍没有可识别对象或判定特征时，再询问。
- 巡逻按区域边界飞闭合环。边界不可通行时，先检查用户已给或库中登记的适用外围范围；仍无可用范围再询问。
- 用户明确要求固定往返航线扫内部时，当前执行入口尚不支持，说明具体缺口并可交付该航迹的只读预览；改变为边界巡逻或自主探索需用户接受。
- 只有用户明确说“跟踪”“跟随”时才启用跟踪。
- 用户明确要求载荷（红外、激光雷达等）时才按载荷筛选；普通目视搜索不加载荷条件。

**相对基准**：沿用用户或会话已明确的参照。只有方向+距离且明确指定单架执行机时，使用该机有来源的当前位置；状态库坐标只是起飞点记录，不能冒充实时位置。用户已指定登记起飞点或会话已采用该基准时直接使用；确需当前位置而工具无法取得时，才询问位置或可否使用起飞点。未指定执行机时用地点库“默认位置”；多机共同参照先从上下文解析，仍无法唯一确定再询问。

指定速度需核对参与机资源记录的 `max_speed`。超过上限时指出冲突并询问，不自动截到上限；只做咨询时可展示明确标为待接受的限速备选，不能称原速度要求已满足。成本或dry-run成功不证明机型速度限制已核对。

历史复搜先沿用会话中的目标特征，缺少时查询可访问的历史记录；两者均无法取得才询问。离线入口已说明不支持某种历史查询时，不换子命令或遍历不可读目录反复尝试同一能力。

**先核对明确的完成条件**：
- 周期巡逻需要定时启动、间隔等待或跨趟补能调度，当前任务入口未提供；`laps` 仅表示同一次任务内连续绕行。保留单趟圈数、间隔和持续时间，直接说明调度缺口，完成可独立进行的地点、机况查询及单趟只读预览；预览标为周期任务的一部分，执行替代方案需用户接受。
- “找目标，找到后仍把整区搜完/建图”是搜索的完成条件，不因“建图”二字就判成两种联合任务。当前 `ALL_TARGETS_FOUND` 按下述规则返航，且覆盖航迹不认证整区覆盖；不能承诺这一条件已实现。说明缺口并保留原要求，不要求用户在已经明确的意图间重新二选一。
- “至少找出N个相同特征的对象”需要物理实体去重计数，不能复制同一描述N次作为N个目标。当前目标清单不保证这项数量条件；按 target-detection 说明边界。不同外观的同类目标仍可分别搜索。
- “必须保证含往返、起降的总时长”与每区 `search_timeout` 不同；当前水平成本与预算不能提供全任务保证。不能把默认速度下的估计超限说成所有允许参数下都物理无解，也不能承诺提高速度后必然满足总时限。
- 用户指定跟踪时长时，先说明当前 profile 固定、不支持自定义；不能把默认 profile 或搜索时限当成该时长。未满足的方案只能明确标作待用户接受的备选，不能称原请求已完整完成。
- 纯飞行/多途经点尚未接入当前完整任务入口和中央作业契约；直接说明接口缺口，并用单项航迹工具完成可支持的路径预览，不追问“到了以后做什么”。混合任务类型和同一架机内的步骤顺序已支持；固定到不同无人机的步骤先后顺序不保证，按 check_task.py 的 gaps 说明。不通过拆单返航、改任务类型或重排顺序替代原请求。

**候选机**：
- 按语义识别机号的角色：明确派遣的机号或候选列表才限定执行机；用作位置参照、查询对象或资源说明的机号不等于执行机。例如“在 UAV-002 左前方探索”中的 UAV-002 只是位置参照。
- 没点名、没说具体架数（“派无人机去搜”），或只是说明资源（“我有五架”）：全部合格机都是候选，由算法决定出动几架，不必追问。
- 要求出动架数（“派两架去搜”）：在数值分配中保留 `constraints.required_drones`，表示恰好这么多架实际作业，不能用待命机凑数。候选不足或约束无解时说明原因，保持数量要求。
- 某作业限定“从这些机中选择”时使用 `constraints.allowed_assignments`；明确某机独占某作业时使用 `fixed_assignments`。允许集合不等于出动数量，不用额外指定数量来代替它。
- 点名机不可达或不可用时，仍用全量候选查询给出可替代的机号，不能拿一次 `LIMIT` 样本概括“整个机队都到不了”。判断可行性要同时看转场往返和作业覆盖/巡逻航程；转场可达不等于任务可行。未点名时把作业中心传给 `prepare_candidates` 做附近预筛；不要用最近 K 架替代可行筛选。

**默认值**：航高 1.2 m；巡逻 1 圈；搜索时限 1200 s；任务结束后返航并降落（用户明确要求结束后不返航时，改为原地悬停等待指令）；速度不指定时用工具默认值。默认值可能造成“参数性不可行”：成本筛查的 `candidate_screening.diagnosis` 会指出最近候选和实际绑定约束；航程足够但默认转场速度（1.2 m/s）下时间不够时，应说明可指定速度（不超过该机 `max_speed`）后重算，不能概括为“所有无人机航程不足”。指定全局速度时，成本工具会按 `max_speed` 自动以 `SPEED_LIMIT` 排除不支持该速度的候选，不需要手工缩小候选范围。

无目标探索/巡逻完成后悬停，用中央 `on_search_complete=HOLD` 表达；完整原始动作仍保留工具生成的备用返航/降落段，不能自行删段，见 flight-control。离线交付同时列出策略与备用段，说明不能把整条原始动作直接连续发布。带目标时 `ALL_TARGETS_FOUND` 是另一个待决策条件，不能宣称仅加 HOLD 就改变了它的既有返航规则。

## 三、按需规划与执行

按整句判断请求，“只规划”“先给方案”“确认后再执行”等限定优先。“派……”“去……”“巡逻……”“开始搜索……”等明确动作指令即为本次执行授权；信息齐全且方案满足用户要求时，连续完成规划、校验和中央下发，不再询问是否执行。只规划完成计算后按第五节交付；要求确认后执行时出确认卡等待。需要改变用户明确约束的备选方案也先说明差异并取得接受。故障补做按原任务授权直接下发。

根据用户所需结果和已有数据，补齐当前缺少的部分；单项请求在该项完成后即可交付，不要求经过完整链路。

识别为执行请求后、开始规划前，按 AGENTS.md 做环境检查。`online_execution_configured=false` 时，完成当前可支持的离线规划和校验，记录缺失组件，按第五节用日常语言说明未下发的原因；无需让用户再次确认执行意图。环境接通后，依据最新机况、地图和中央预检判断方案是否需要重算。多步骤/混合类型先按 [references/combined-tasks.md](references/combined-tasks.md) 整理并用 `check_task.py` 核对；跨机固定顺序等接口无法表达的部分直接说明缺口，不把它们全部填为一种区域作业再尝试求解。

| 当前缺少的内容 | 使用已有技能 | 返回内容 |
|---|---|---|
| 地点、状态、资源事实 | data-query 原SQL查询 | 真实记录 |
| 合格候选机与预算 | data-query 的 prepare_candidates.py | candidates、excluded |
| 明确的数值区域 | spatial-compute 的 resolve_jobs.py；相对位置先用 calc_offset.py | jobs |
| 多步骤能力核对 | mission-planning 的 check_task.py | 类型/参数/顺序检查、gaps和route |
| 作业与转场成本 | trajectory-generation 的 planning_routes.py，operation=costs | candidates、jobs、costs、constraints及prepared |
| 无人机归属和访问顺序 | mission-orchestration 的 allocate.py | assignments、owners、unused及求解证据 |
| 分配后的具体航迹和航高 | trajectory-generation 的 planning_routes.py，operation=build | 原始WGS84航点、每机steps、航程估计 |
| 动作序列与格式校验 | flight-control 的 assemble_plan.py | 完整动作产物、dry-run结果、逐机报告摘要 |
| 目标配置校验 | target-detection 的 validate_targets.py | 目标清单格式、机号记录校验结果 |

成本输入接收候选和数值区域；分配只接收候选预算、作业标识、成本及明确约束。复用成本结果的 `constraints` 保留固定归属和圆形巡逻的单机要求；圆形搜索可由两机共担，不套用巡逻的单机约束。用户另有逐作业候选集合或数量要求时一并保留，不额外增加用户未要求的出动数量。最终航迹接收同一次 `cost_estimate` 和 `allocation`，不能把归属结果当作航点结果使用。只要已有兼容的数值输入，分配咨询可以直接求解，不必查询地点或生成航迹。

完整只规划方案需按 flight-control 对每架机做dry-run；有目标时按 target-detection 做本地目标校验，保存完整动作和各项验证范围，面向用户按第五节交付。在线环境齐全的执行请求使用组装好的原始 WGS84 动作，继续本节中央下发操作；只读计算和待确认方案不启动感知。

**整理作业**：一个动作步骤一个作业；同一区域的不同动作拆成多个作业。
- 每步分别写 `task_type`（`search`/`patrol`）、`laps`（只巡逻）、`search_timeout`（只搜索）；同一区域先巡逻再搜索时用两个不同 `job_id`。用户要求“先……再……”时在成本输入加 `"ordered": true`。多步骤或混合类型先读 [references/combined-tasks.md](references/combined-tasks.md)，并用 `check_task.py` 分别核对类型、参数和顺序。
- 地名：`{"place":"教学楼"}`。用户指定了形状、尺寸就一并写入，如 `{"place":"教学楼","shape":"circle","radius":5}`。
- 经纬度：`{"name":"…","center_lon":…,"center_lat":…,"shape":"circle","radius":…}` 或 `"shape":"rectangle","length":…,"width":…`。`name` 写用户对该区域的叫法，没有就写“区域1”“区域2”。
- 相对位置：按第二节“相对基准”确定参照，再用 data-query 查相应记录、用 spatial-compute 的 `calc_offset.py` 算出中心。地点基准有登记区域时用区域中心 `region_center_*`，没有时用该地点的 `longitude/latitude`。偏移后的新区域从用户描述和上下文取得形状、尺寸。
- 用户指定“某机去某区域”时，在该作业里加 `"uav_id"`。
- 地名由 data-query 查询匹配，区域完整性由 spatial-compute 的 resolve_jobs.py 校验。缺项先从查询结果和上下文补齐，仍只有点位且无范围才询问形状和尺寸。

**确认卡**：仅在用户要求先确认，或需接受改变明确约束的备选时，按第五节格式输出。卡片使用 flight-control 组装的原始 WGS84 序列；等待期间不启动感知或下发。普通执行请求直接使用组装结果进入中央流程。

**用户对确认卡的回复**（只对最近一张卡有效）：

| 回复 | 处理 |
|---|---|
| 确认（“确认”“执行”“可以”“开始”等，不带修改或疑问） | 进行下述中央下发操作 |
| 修改（改参数、换区域、换机、点名执行机） | 只改用户提到的部分并重算，旧卡作废；明确说“改后执行”则校验后下发，否则输出新卡并写明差异 |
| 取消、否定 | 回复“已取消，未下发任何任务” |
| 追问方案 | 按分配结果回答；卡片仍待确认，不下发 |
| 其他新请求 | 旧卡作废，按新请求处理 |

用户确认时若找不到对应方案、编号或动作序列，先从本次会话产物恢复；无法恢复才重新规划并出卡。

**中央下发操作的顺序**（有依赖，不能并行）：
1. `mission_client.py status`：`execution_enabled` 为 true；有目标时 `perception_ready` 为 true；要跟踪时 `target_actions_ready` 为 true；参与机在 `fleet` 里 `available=true`。不满足就停止并报告。
2. 有目标时按 target-detection 为每架参与机准备感知（未运行则 start，已运行则 query），全部机共用同一个 `search_id` 和目标清单；完成后再读一次 `status`，取各机 `fleet.<uav_id>.perception`。
3. 每架机 `register-plan`（可并行；`batch` 使用本次组装的原始 WGS84 序列，有已确认卡则与卡片一致）→ 一次 `authorize`（记录真实用户指令，写法见 flight-control）→ `preview` → 立即 `submit`。
4. 任一步失败：不提交；已为本任务新启动的感知，用 target-detection 的停止命令关闭；报告失败的环节和原因，不自动换方案重试。

提交后只回复“已提交”和各机安排，不轮询等待任务完成。

用户看过分配咨询或只规划结果后要求执行：更新状态事实，取得与当前方案对应的原始 WGS84 序列，校验后下发；之前 dry-run 的本地坐标序列不能注册。需要改变用户明确要求时才说明差异并询问。

## 四、运行中处理

先用 `mission_client.py get` 读最新快照，其中 `revision` 就是下一次控制的 `expected_revision`。命令写法见 flight-control 的 [运行控制](../flight-control/references/runtime-control.md)。

| 情况 | 处理 |
|---|---|
| 目标发现通知 | 用一两句话报告哪架机发现了什么，不需要操作 |
| 决策 `TARGET_ASSIGNMENT_REQUIRED` | 在 `assignment_options` 里选 `eligible=true` 且 `distance_m` 最小的机，`decide assign_target`；没有可选机就报告并保持等待 |
| 决策 `ALL_TARGETS_FOUND` | 搜索完成，全部返航：没有机在跟踪时 `decide return`（scope=mission）；有机在跟踪时，该机 `return` 加 `after_tracking=true`，其余每架机 `return`（scope=uav） |
| 决策 `TRACKING_FINISHED` | 中央已自动恢复该机原搜索：还有目标没找到 → `decide continue`；目标已全部找到 → 该机 `decide return` |
| `exceptions` 里出现 `WAITING_DECISION` | 按下方故障处置 |
| 用户要求暂停、继续、全部返航、取消、停止跟踪 | 分别 `control` pause、resume、return、cancel、stop_tracking |
| 任务结束（SUCCEEDED、PARTIAL、FAILED、CANCELED） | 报告终态、各机作业完成情况、已找到和未找到的目标 |
| 询问进度或原因 | `get`、`events` 只读查询，必要时查执行历史；不重新起飞 |

**故障处置**（某架机出现异常）：
1. 召回故障机：`control return`，scope=uav；该机的异常随之结束。其余机不暂停，继续原计划。返回 ACCEPTED 即可做下一步，召回是否生效看后续事件。
2. 重新 `get` 一次，从最新快照找出故障机未完成的作业（`region_jobs` 中状态不是 SUCCEEDED 的项）和尚未找到的目标。`step_id` 是该机动作序列的步骤号，对照原任务下发的动作序列和作业顺序得到地点；对不上时不补做，报告未完成的作业。未完成的作业整区重做。
3. 重新查询候选和计算这些未完成作业的成本，再交数值分配：候选查询的 `exclude_uavs` 排除原任务全部参与机（它们仍属于原任务）；成本和航迹的基准航高须高于原任务最高航高至少0.3米，并经航迹工具检查升限，不能在 allocate 中调整高度。
4. 有可行方案：不出确认卡，组装动作后按第三节中央下发操作作为新任务提交：只搜未找到的目标，`search_id` 用新的 `task_key`，`policies` 沿用原任务（`get` 快照里的 `policies`；有 `tracking_target_ids` 时只保留这次要搜的目标）。下发后按第五节报告。没有可行方案：报告这些作业未完成。
5. 召回请求被拒绝时，如实报告阻塞，不另发新请求。

## 五、回复格式

**用户表达**：按 AGENTS.md 的日常语言规则回复。普通任务先说实际进度、执行机和任务安排，再说明影响执行的原因或限制；单机简单任务用短段落，多机或多个作业才按需列表。正常计算、筛选和校验留在内部，不逐步播报工具过程。技术字段、动作数量、内部编号和配置缺项清单只在用户调试或索要相应数据时展示。若本轮 `assemble_plan.py` 的 `summary.participants[*].actions` 存在（`UAV_SHOW_ACTIONS` 开启），按 flight-control 的说明在最终回复中用 JSON 代码块展示动作序列；没有则不展示。动作序列属于调试信息，可以展示；回复中不要出现 dry-run、离线校验、本地校验、mock、submitted=false、中央下发通道、任务入口、规划工具等内部术语，用“已检查”“尚未下发”“当前能力”这类日常说法。

**单项查询或计算**：回答用户所问字段、工具结果及必要限制即可。额外的距离、电量、可行性结论也必须有对应工具结果；没有计算过就不追加。资源硬条件筛选只证明候选条件通过，完整任务可行性还依赖实际区域成本、航迹和当前场景限制。

**信息不足**：仅对查询和上下文仍无法补齐、实际阻塞任务的缺项，一次提出简短问题；有多个候选时给出名称或区别供选择。已查到的值直接采用，常规默认值在结果中简要注明。

**能力不足**：说明无法完成的具体步骤和已完成部分，保留用户原要求；不把接口限制说成用户意图不清，也不以“是否继续”代替可独立完成的工作。所有候选被筛掉时，报告最近候选、距离和实际绑定约束（航程/时间），不能只引用失败原因标签或笼统归因于航程。

**确认卡**：

```
方案已准备好，尚未下发：UAV-003 搜索教学楼，UAV-005 搜索食堂，寻找穿红色上衣的人，结束后返航降落。
区域按地点记录：教学楼 12×11 米，食堂 11.5×9 米。
| 无人机 | 作业顺序 | 航高 | 预计航程 | 预计剩余电量 |
| UAV-003 | 教学楼 | 1.2 m | 99.2 m | 70.2% |
| UAV-005 | 食堂 | 1.5 m | 64.5 m | 77.1% |
每个区域搜索上限为默认的20分钟。
你要求先确认，回复“确认”后执行；需要调整可直接说明。
```

- `task_key` 与对应的完整动作保存在内部，用于关联用户确认和后续执行。
- 任务：搜索写“搜索<目标>，发现后只报告，不跟踪”（要求跟踪时写“发现后接近并跟踪”）；探索、建图写“探索（无目标）”；巡逻写“巡逻 N 圈”。
- 区域：每个作业写名称、来源、形状和尺寸，取自区域或最终航迹结果的 `jobs[]`：`area_source=registry` 写“地点库登记区域”，`user` 写“按你给的范围”。相对位置再写明基准点，如“教学楼区域中心东北 20 m”。
- 表格同分配咨询；两架机共用一个区域时，作业顺序写成“中央广场（1/2）”。
- 参数：保留用户要求和影响确认的航高、圈数、搜索时限及结束动作；采用默认值时简要注明，避免罗列全部内部参数。
- 与原要求不符或影响判断的限制，用日常语言说明，例如“航程和电量估计尚未计入起降”。用户明确约束未满足时报告原因，不以确认卡替代约束满足。
- 动作使用 flight-control 的 `assemble_plan.py` 直接读取 build 结果组装并保存。需要文件时提供“完整方案”链接；字段位置和完整 JSON 按用户明确请求提供。

**执行任务提交后**：

```
任务已下发：由 UAV-003 搜索教学楼内穿红色上衣的人，完成后返航降落。目前尚未收到起飞消息。
```

只有收到起飞或执行事件后才写“正在执行”；缺少反馈时说“尚未收到起飞消息”，不据此断言飞机尚未起飞。完成情况以实际任务结果为准。任务编号在用户查询编号或排查问题时提供。

**下发失败**：说明任务未下发及具体原因，例如“UAV-003 正在执行其他任务，本次任务尚未下发”。仅在清理操作影响用户时补充说明。

**只规划或暂时无法执行**：说清已生成的方案和当前状态，按需列执行机、区域、圈数、结束动作及预计航程、电量。数值取本次方案的回传结果；完整动作和方案已保存。展示估计数值时紧邻说明影响判断的范围，如“航程和电量估计尚未计入起降”。无法执行时用一句话说明服务或设备问题，未结合地图核对障碍时说明“路线尚未核对现场障碍”，不把计算成功说成已经飞行。所有候选被筛掉时，按 `candidate_screening.diagnosis` 说明最近候选、距离、哪项下界不满足（航程或时间），以及指定速度后重算的可行路径。

例如：“饭否东西20米、南北10米的矩形巡逻方案已生成，拟由 UAV-410 沿边界巡三圈后返航。飞行控制服务尚未接通，任务还没下发；路线也尚未核对现场障碍。”

**故障通知后**：说明哪架机出了什么异常、已做的处理（召回请求是否被接收）、其余机状态，以及补做安排；没有可行方案时说明哪些作业未完成。

**分配咨询**：按 mission-orchestration 的回复格式。

## 注意事项

- 地点库的 `longitude/latitude` 是入口，`region_center_*` 是区域中心，两者用途不同；相对位置的基准按第三节“整理作业”选取。
- 航高 `flight_alt` 是任务参数，不是状态库的 `altitude`（记录的当前高度）。
- 多机任务的各机航高由任务航迹工具按基准值间隔0.3米计算。该默认错高不等于用户要求的严格统一航高；无法同时满足时说明冲突。
- 确认卡仅用于用户要求的确认环节或待接受的需求变更；明确执行请求、运行控制、待决策处理和故障补做按对应流程继续。
- dry-run 只证明格式和坐标转换合法；分配只校验给定数值成本和预算，最终航迹报告水平航程及电量估计，未覆盖起降、跟踪和搜索时间上界时明确披露；在线、占用、感知就绪由中央在注册和预览时检查。
- 同一请求重试沿用原 `request_id`，新动作才用新 ID；结果不明时先 `get`/`events` 再决定。
