# 任务总路由（互斥决策树）

## 第零步：能力边界前置拦截（最高优先，命中即直接拦截反问）

凡指令明确要求以下**当前系统确实无法覆盖的能力**时，**禁止进入规划工具、禁止偷换任务意图兜底、禁止生成动作 JSON**，直接读 [plan-delivery.md](references/plan-delivery.md) 按**模板 B（任务无法下发/能力不足拦截）**回复并反问用户是否调整：
- **非平行特殊覆盖路径**：明确要求“逐圈环形推进 / 同心圆逐圈覆盖 / 螺旋式由外向内或由内向外收拢”（当前区域覆盖仅支持**弓字形/平行往复条带**）；
- **持续流式进度回报**：要求“边巡边持续回报进度”；
- **禁限飞绕行 / 实时避障控制 / 通信链路保障**：要求“禁限飞区按批准航线自动绕行”“遇障自动升高规避后再恢复贴边”“全程保持通信链路”；
- **其他未实现完成条件**：跨趟周期/定时循环巡逻、实体去重计数。

> **合法备选兜底 vs 非法偷换意图**：仅当任务本身在能力边界内，因指定机航程/电量/时间/升限/空闲状态不足导致无法完成时，才允许规划换机/调高/调速备选方案并附动作 JSON 让用户确认；**绝不允许**把上述超界能力偷偷改成普通探索或常规巡逻并声称已完成规划。

## 第一步：按顺序命中唯一入口（严禁同时预读 `artifact-pipeline.md` 与 `task-graphs.md`）

从上到下匹配**第一条**命中的规则，只读对应参考页：

1. **复杂任务图（最高优先）**：指令包含以下**任一**特征 → **只读 [task-graphs.md](references/task-graphs.md)**（只规划不下发）：
   - 独立接口动作：`扫描(scan)`（如扫描战壕/道路）、`录像`、`拍照`、`持续观察`、**纯点到点飞行后的**`悬停/等待/盘旋`、`切换模式(红外/高清)`、`发现后报告/跟踪`、自定义跟踪或持续时长；
   - 复杂逻辑：条件分支（找到/没找到/超时）、发现后动态位置（“找到后以它为中心/由最近机接手”）、跨机先后依赖（“A机完成后B机再…”）、或含**纯“飞往/去某地”途经点**的混合任务。
   - **防误判边界**：单区/多区搜索、弓字形覆盖或巡逻前的“飞抵/直飞/转场至该地（或相对偏移点）后开展作业”，以及“作业完成后原地待命/悬停/盘旋”，均由常规 `--pipeline` 原生支持（自动含转场段，通过 `return_to_home: false` 按单程计算并以 `hover` 结束），**不要**因此命中本条拆成 `transit`/`hover`，应直接走规则 2/3。
2. **同机多步混合**：无上述第 1 类特征，但同一架机内混合 `search`/`patrol` 或要求同机“先…再…”顺序 → 读 [combined-tasks.md](references/combined-tasks.md) + [artifact-pipeline.md](references/artifact-pipeline.md)。
3. **普通搜索 / 弓字形覆盖 / 边界巡逻 / 可行性评估**：单区或多区搜索（含无目标探索、两机分区共担）、**弓字形区域覆盖（凡表达全面往复扫描的近似说法，如拉网式、筛网式、梳状等类似表述，均由模型按语义统一归类为弓字形覆盖）**、边界巡逻，或“只规划/只回答可行性” → **只读 [artifact-pipeline.md](references/artifact-pipeline.md)**。

### 按需附加页（仅在对应环节触发时读，不预读）
- **准备最终交付回复**（完整方案、确认卡、能力拦截或交付落盘）→ [plan-delivery.md](references/plan-delivery.md)（**必须严格套用其中的固定 Markdown 模板，禁止自由发挥**；常规规划交付无需再读 `flight-control/SKILL.md`）
- **任一计算/校验报错、不可行或返回条件备选** → [diagnostics.md](references/diagnostics.md)
- **中央下发 / 处理确认卡回复**（**仅当 `AGENTS.md` 开关为 `ONLINE_EXEC` 时可用；当前 `PLANNING_ONLY` 模式禁止读取与调用**）→ [online-submission.md](../flight-control/references/online-submission.md)
- **已提交任务的运行控制、待决策或故障补做**（仅 `ONLINE_EXEC` 模式）→ [runtime-control.md](../flight-control/references/runtime-control.md)

## 第二步：授权、结束动作与约束边界
- **盘旋 / 悬停 / 结束动作统一规则**：凡要求“盘旋/悬停/待命/原地待命”，或用户**未指定**结束后是否返航的任务，一律**不返航、按单程（去程+作业）计算、任务结束后原地悬停（`hover`）**；仅当用户**明确要求返航/返回起飞地/降落**时，才计算往返并在末尾返航降落（`return_to_home: true`）。
- **执行授权**：当前 `PLANNING_ONLY` 模式下，明确动作指令与只规划请求均连续完成规划、校验与交付落盘后直接按 `plan-delivery.md` 模板 A 回复“方案已生成并检查，尚未下发”，不调用 `mission_client.py` 或启动感知；仅 `ONLINE_EXEC` 模式下再按授权下发。“只规划”“只回答可行性”“确认后执行”始终优先遵守。
- **改变原约束须待接受**：在能力边界内的备选方案（换机、减少点名机、共担改单机、改速/改航高、跨机顺序改并行等），必须说明差异并等待用户接受，均不得静默采用；超界能力则直接拦截反问，不做偷换兜底。
- **机号与动作保真**：区分执行机与位置参照机；保留点名参与机、恰好出动数量（`required_drones`）与明确先后顺序；严禁把纯“飞往”篡改成区域 `search`。
- **确认卡有效范围**：确认仅对应最近一张待确认卡；修改后旧卡作废；故障补做沿原任务授权按 `runtime-control.md` 处理。
