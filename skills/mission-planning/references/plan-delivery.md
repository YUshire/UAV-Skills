# 完整方案交付模板与核对清单

> 仅在交付完整规划、确认卡、执行结果或故障补做时读；单项查询/预览按对应技能简短回复。**常规规划交付按本页闭环，无需另读 `flight-control/SKILL.md`。**

## 交付前 4 项快速核对（核对 1 次直接回复，不重复规划）

1. **数值、距离与告警依据**：
   - 直接采用 `summary` 返回值（`estimated_range_m`、`estimated_battery_after`、`takeoff_to_jobs_m`、`reserved_airborne_time_s`、`max_distance_m`）；**严禁**用局部坐标 X/Y 单轴分量心算直线距离，严禁跨机/跨区张冠李戴。
   - 展示预计航程或电量时，紧邻注明统计范围（采用 `summary.budget_scope`，如“航程和电量估计尚未计入起降与搜索超时上界”）。
   - 任务图分支的 `violations` / `pending` 告警（特别是 `TIME_RESERVATION` 超预算）必须如实告知；部分失败时开头说明已完成与受阻范围，后续执行条件须保留未解决项。
2. **交付请求 JSON（仅当普通任务 `assemble_plan` 校验通过 `artifact_created=true` 时写入）**：
   - 使用 `write_file` 保存至 `artifacts/requests/delivery_<task_key>.json`（勿把 pipeline 输入文件当作交付请求 JSON；**`assemble_plan` 整体失败时禁止写该文件，严禁篡改上游 `build` 产物跑子集**）：
   ```json
   {
     "task_key": "<summary.task_key>",
     "artifact_file": "<assemble_plan返回的artifact_file>",
     "participants": ["UAV-003"],
     "targets": [],
     "policies": {"land_on_return": true}
   }
   ```
   - 无目标结束后原地悬停：在 `policies` 加 `"on_search_complete": "HOLD"`。
   - 要求发现后跟踪：在 `policies` 加 `"on_first_confirmed": "APPROACH_AND_TRACK", "tracking_target_ids": ["<target_id>"]`，并说明 approach/tracking profile 待执行提交时按 `status` 补齐。
   - 复杂任务图保留原图 JSON 即可；纯“只回答可行性”咨询不写交付请求 JSON。
3. **动作 JSON 强制展示规则（只要做出了规划就必须展示）**：
   - **必展条件**：除非本次任务完全无法规划（`INFEASIBLE`/`BLOCKED`）或工具报错，否则**但凡做出了规划**（无论是直接满足原意图，还是原意图受限后给出替代/降级方案待用户确认，无论是普通 `--pipeline` 还是复杂任务图 `plan_task_graph`），只要工具返回了 `summary.participants[*].actions` 或 `summary.scenarios[*].assignments[*].actions` 且 `summary.show_actions` 不为 `false`（当前默认 `true`），回复中**必须**用合法 ` ```json ` 代码块逐机完整展示动作序列（保留 `count/first/last` 折叠，**严禁遗漏、严禁用文字概括替代、严禁用“同上”“其余类似”、省略号或注释**，不混入已放弃版本）。
   - **不展示条件**：仅当任务完全无法规划/报错、纯可行性咨询未生成规划，或 `summary.show_actions` 显式为 `false` 时才不展示，不另读 `raw_batch` 或凭空手写动作。
4. **日常中文与状态边界**：
   - 先说结论、执行机与安排，再说影响判断的限制；同一限制只说一次。
   - 禁用内部术语（`dry-run`、`离线校验`、`本地校验`、`mock`、`submitted=false`、`中央下发通道`、`任务入口`、`规划工具`、脚本与产物绝对路径）；下发状态一律以实际工具返回为准（仅当 `submit` 返回 `ACCEPTED` 才写“已下发”，未提交时写“方案已生成并检查，尚未下发”），并注明“路线尚未核对现场障碍”“目标配置已检查，实际识别能力尚未验证”。

## 标准回复模板

### A. 方案 / 确认卡交付模板（尚未提交时）
```
方案已生成并检查，尚未下发：UAV-003 搜索教学楼（寻找穿红色上衣的人，发现后只报告，不跟踪），UAV-005 沿食堂边界巡逻 2 圈，完成后返航降落。
区域来源：教学楼（地点库登记区域，12×11 米），食堂（按你给的范围，以食堂区域中心东北 20 米为中心、12×8 米矩形）。

| 无人机 | 作业顺序 | 航高 | 预计航程 | 预计剩余电量 |
|---|---|---|---|---|
| UAV-003 | 教学楼（1/2） | 1.2 m（默认） | 99.2 m | 70.2% |
| UAV-005 | 食堂 | 1.5 m | 64.5 m | 77.1% |

默认参数：搜索上限 20 分钟；结束后返航降落。航程和电量估计尚未计入起降与搜索超时上界；路线尚未核对现场障碍；目标配置已检查，实际识别能力尚未验证。

（有可下发动作序列时必须紧跟展示，每机一个合法 JSON 代码块，不可省略）
**UAV-003 动作序列**：
```json
[ ...直接填入 summary.participants 中该机的 actions 原数组... ]
```
（若需用户确认或接受备选差异，结尾写：回复“确认”即按上述方案/差异执行；需要调整可直接说明。）
```
- 两机共担同一区域时，作业顺序标注 `区域名（1/2）`、`区域名（2/2）`；单机简单任务可用短段落代替表格。

### B. 在线提交后 / 下发失败 / 故障通知后
- **已提交**：`任务已下发：由 UAV-003 搜索教学楼内穿红色上衣的人，完成后返航降落。目前尚未收到起飞消息。`（收到起飞事件前不写“正在执行”）。
- **下发失败**：一句说清未下发及原因（如“UAV-003 正在执行其他任务，本次任务尚未下发”）。
- **故障通知后**：说明故障机与异常、召回是否受理、其余机状态与补做安排（无可行方案时列出未完成作业）。
