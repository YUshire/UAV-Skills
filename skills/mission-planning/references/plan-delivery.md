# 完整方案交付

仅在交付完整规划、确认卡、执行结果或故障补做安排时读；单项查询按对应技能回复。

**用户表达**：按 AGENTS.md 的日常语言规则回复。普通任务先说实际进度、执行机和任务安排，再说明影响执行的原因或限制；单机简单任务用短段落，多机或多个作业才按需列表。正常计算、筛选和校验留在内部，不逐步播报工具过程。技术字段、动作数量、内部编号和配置缺项清单只在用户调试或索要相应数据时展示。动作 JSON 的展示按下一段检查项处理；其余回复不要出现 dry-run、离线校验、本地校验、mock、submitted=false、中央下发通道、任务入口、规划工具等内部术语，用“已检查”“尚未下发”“当前能力”这类日常说法。同一状态或限制通常说明一次，不在开头和结尾重复整段内容。

**交付前核对一次**：遵循 AGENTS.md 的停止条件，仅检查下列与本次交付相关的项目，修正具体缺漏后直接回复，不以检查为由重复整轮规划：

- **必需内容**：本次结果、尚未完成部分和影响判断的限制应与工具证据一致。格式校验成功只按其验证范围表述，不扩大为整个任务或实际效果已验证。部分参与机动作校验失败时，开头说明只完成了哪些部分，逐机区分已计算航迹、动作已检查和检查失败；保存了几何方案或请求文件，不代表完整动作方案已通过检查。后续执行条件须保留尚未解决的检查失败，不能只写服务接通、核对机况后即可下发。
- **数值与能力依据**：数值保留其对象、单位和统计范围（必须注明工具 `budget_scope`，如“航程和电量估计尚未计入起降与搜索超时上界”），分项不能写成总量、总量不能写成分项；起飞点到区域直线距离直接取 `summary` 中的 `takeoff_to_jobs_m`，严禁拿本地坐标 X/Y 单轴分量当直线距离。任务图分支的 `pending`/`violations` 告警（如 `TIME_RESERVATION` 超预算）必须如实告知。设备登记参数不推导为未经验证的识别能力或效果保证；证据不足时按 AGENTS.md 标为未验证。
- **离线请求 JSON**：普通任务离线交付（`assemble_plan` 校验通过）时，交付前须用 `write_file` 将 `task_key`、动作产物 `artifact_file`、参与机、`targets` 与拟用 `policies` 保存为本次唯一请求 JSON（不要误把 pipeline 输入文件当作交付请求 JSON）；复杂任务图离线交付保留原图文件。
- **动作 JSON**：按 [flight-control 的动作展示开关](../../flight-control/SKILL.md) 与本次 `summary.show_actions` 交付；开关含义、实际返回动作及待接受方案均以该规范为准。`summary` 已含全部交付字段，不要为了确认开关或区域信息再去 `grep` 源码或整份读取 `flight_actions`/`planning_routes` 产物。
- **内容自足**：需要交付的不同参与者、步骤和字段均明确写出，不用“同上”“其余类似”或省略号代替必需内容。JSON 保持合法，不插入注释或文字占位；工具已返回的 `count/first/last` 折叠结构可原样展示。

**信息不足**：仅对查询和上下文仍无法补齐、实际阻塞任务的缺项，一次提出简短问题；有多个候选时给出名称或区别供选择。已查到的值直接采用，常规默认值在结果中简要注明。缺信息不是不可行，不要把缺少区域、航高或速度直接报成“不可达”。

**确认卡**：

```
方案已准备好，尚未下发：UAV-003 搜索教学楼，UAV-005 搜索食堂，寻找穿红色上衣的人，结束后返航降落。
区域按地点记录：教学楼 12×11 米，食堂 11.5×9 米。
| 无人机 | 作业顺序 | 航高 | 预计航程 | 预计剩余电量 |
| UAV-003 | 教学楼 | 1.2 m | 99.2 m | 70.2% |
| UAV-005 | 食堂 | 1.5 m | 64.5 m | 77.1% |
每个区域搜索上限为默认的20分钟。
你要求先确认，回复“确认”后执行；需要调整可直接说明。
```

- `task_key` 与对应的完整动作保存在内部，用于关联用户确认和后续执行。
- 任务：搜索写“搜索<目标>，发现后只报告，不跟踪”（要求跟踪时写“发现后接近并跟踪”）；探索、建图写“探索（无目标）”；巡逻写“巡逻 N 圈”。
- 区域：每个作业写名称、来源、形状和尺寸，取自区域或最终航迹结果的 `jobs[]`：`area_source=registry` 写“地点库登记区域”，`user` 写“按你给的范围”。相对位置再写明基准点，如“教学楼区域中心东北 20 m”。
- 表格同分配咨询；两架机共用一个区域时，作业顺序写成“中央广场（1/2）”。
- 参数：保留用户要求和影响确认的航高、圈数、搜索时限及结束动作；采用默认值时简要注明，避免罗列全部内部参数。
- 与原要求不符或影响判断的限制，用日常语言说明，例如“航程和电量估计尚未计入起降”。用户明确约束未满足时报告原因，不以确认卡替代约束满足。
- 动作使用 flight-control 的 `assemble_plan.py` 直接读取 build 结果组装并保存。需要文件时提供“完整方案”链接；字段位置和完整 JSON 按用户明确请求提供。

**执行任务提交后**：

```
任务已下发：由 UAV-003 搜索教学楼内穿红色上衣的人，完成后返航降落。目前尚未收到起飞消息。
```

只有收到起飞或执行事件后才写“正在执行”；缺少反馈时说“尚未收到起飞消息”，不据此断言飞机尚未起飞。完成情况以实际任务结果为准。任务编号在用户查询编号或排查问题时提供。

**下发失败**：说明任务未下发及具体原因，例如“UAV-003 正在执行其他任务，本次任务尚未下发”。仅在清理操作影响用户时补充说明。

**只规划或暂时无法执行**：说清已生成的方案和当前状态，按需列执行机、区域、圈数、结束动作及预计航程、电量。数值取本次方案的回传结果；仅按实际产物说明保存了几何方案、部分动作还是完整动作，以及相应检查范围。展示估计数值时紧邻说明影响判断的范围，如“航程和电量估计尚未计入起降”。无法执行时用一句话说明服务或设备问题，未结合地图核对障碍时说明“路线尚未核对现场障碍”，不把计算成功说成已经飞行。失败时按 [阶段诊断](diagnostics.md) 交付。

例如：“饭否东西20米、南北10米的矩形巡逻方案已生成，拟由 UAV-410 沿边界巡三圈后返航。飞行控制服务尚未接通，任务还没下发；路线也尚未核对现场障碍。”

**故障通知后**：说明哪架机出了什么异常、已做的处理（召回请求是否被接收）、其余机状态，以及补做安排；没有可行方案时说明哪些作业未完成。

**分配咨询**：按 mission-orchestration 的回复格式。
